What changed in this commit (round-5 hardening):

  The previous rounds closed most of the gaps, but missed the directive's
  exact wording: "a hard global maximum of 5 concurrent OR ASSIGNED MiniMax
  sessions". An "assigned" MiniMax session is one whose ``claimed_by`` is
  set (the bus has routed the job to a worker) — even if the worker has
  not yet actively claimed it (``status='offered'``). The round-4 pool
  queries filtered on ``status IN ('claimed','running')`` only, which let the
  global cap overflow by N: N offered jobs could be assigned in parallel to
  N different workers while the cap reported 0/5 full, until each worker
  actively claimed its assigned job and the pool jumped straight from 0
  to N (or N+1 with a new claim). Round-5 fixes the gap.

  * hive/scheduler.py:
    - New constant ``MINIMAX_ACTIVE_STATUSES = ("offered","claimed","running")``
      is the canonical "this job counts against the pool" set. The
      directive makes no semantic distinction between offered and claimed
      for cap purposes ("concurrent OR assigned"), so they're bundled. The
      constant is exported in __all__ so both the per-worker held-lease
      lookup AND the global pool snapshot SQL queries can use it as a
      single source of truth.

  * agent_bus.py:
    - Per-worker held-lease lookup (was:
      ``status IN ('claimed','running')``) now uses
      ``MINIMAX_ACTIVE_STATUSES`` — a worker holding an offered MiniMax
      lease is reported as holding one, so the worker's
      ``active_minimax_lease`` field is set and the per-worker cap is
      consulted correctly on the next claim.
    - Global pool snapshot SQL (was: 'claimed','running') now uses the
      same status set — five offered jobs count as 5 vs the cap, blocking
      a 6th claim. Lease-expiry filter preserved.
    - The 204-fallback response header path now records the LAST
      MiniMaxPool cap-deny reason (was: only checked ``pool.active >= cap``
      post-loop). Per-worker cap denials now surface as
      ``X-Hive-Claim-Result: minimax_pool_saturated`` with a per-worker
      cap detail (not just the global-cap reason). The defensive
      global-cap fallback is preserved for the case where the pool was full
      going IN and no can_assign deny was recorded (all candidates were
      already claimed by someone else mid-loop).

  * test_scheduler.py (+8 new checks, 117 -> 125):
    - ``MINIMAX_ACTIVE_STATUSES == {'offered','claimed','running'}``
    - can_assign denies a 2nd MiniMax claim when the worker already holds
      an offered lease (per-worker cap is exclusive on the MiniMax model).
    - build_pool_snapshot saturates the global cap with 5 offered rows.
    - 3 offered + 2 claimed leases sum at the global cap (3+2=5 saturates).
    - release of an offered lease works the same way as release of a
      claimed lease (pool only sees (worker_urn, job_id) tuples).

  * test_defect_fixes.py (+3 SchedulerDequeueTests, 9 -> 12):
    - test_dequeue_minimax_offered_state_counts_against_global_cap: 5
      offered MiniMax jobs saturate the global pool; 6th MiniMax worker
      gets 204 + X-Hive-Claim-Result=minimax_pool_saturated + global-cap
      detail. Verifies the SQL update for the cap math.
    - test_dequeue_minimax_offered_state_counts_against_per_worker_cap:
      a worker holding 1 offered lease is denied a 2nd MiniMax claim
      with per-worker cap reason in the response header (NOT global cap).
    - test_dequeue_minimax_stale_offered_lease_does_not_count: an expired
      offered lease doesn't count against the pool — fresh MiniMax claim
      succeeds. Verifies the lease-expiry filter applies to offered rows
      too (a crashed worker doesn't permanently reduce capacity).
